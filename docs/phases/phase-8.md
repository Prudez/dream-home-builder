# Phase 8 Handoff

> Repo path: `docs/phases/phase-8.md`.
> Companion: `shared/contract.js` holds the current interface shape. This document references it; it does not duplicate it.

**Phase:** 8
**Date closed:** 2026-08-04
**One-line summary:** Freeform resize (per-room-type min/max sizes removed, replaced by a universal 1×1-cell floor and the plot itself as the only ceiling) and free rotation (drag a handle to spin a room to any angle, rendered via a single SVG transform, collision-checked with real rotated-rectangle intersection).

---

## 1. What shipped

- **Freeform resize**: `catalog_rooms.min_w/min_h/max_w/max_h` dropped from the schema entirely (migration `007_freeform_resize.sql`). The only remaining size floor is universal — `MIN_ROOM_CELL = 1` in `client/src/lib/grid.js` — and the only ceiling is the plot itself (`COLS - room.x` / `ROWS - room.y`), which was already how the old clamp math capped growth; removing the per-room-type clamp was a subtraction, not a rewrite. `default_w`/`default_h` are untouched — they still size a room at initial placement.
- **Free rotation**: placed rooms gained a `rotation` field (degrees, `[0, 360)`, default 0). A new rotate handle (navy circle, ⟳, top-center of the room's unrotated box) drags to set rotation directly from the cursor's angle around the room's center — not snapped to any increment. `RoomArt.jsx` needed exactly one change to support it: every wall/texture/furniture element it already draws gets pushed into the same `els` array as before, and that whole batch is wrapped in one `<g transform="rotate(deg cx cy)">` at render time. None of the individual drawing code changed.
- **Rotation-aware collision**: `collides()` in `client/src/lib/grid.js` now does real rectangle-vs-rectangle intersection via the Separating Axis Theorem (SAT), not a bounding-box comparison — see Decisions below for why this was worth doing properly rather than taking the documented bounding-box fallback the phase prompt allowed. It's used for all four ways a room's shape can change: palette drop, move, resize, and now rotate — the drag-move path threads the room's *current* rotation through (a room being moved keeps spinning the same way it was), and resize/rotate both pass the room's own rotation as part of the candidate shape being tested.
- **`room_rotated` event**: added to `EVENT_TYPES`, logged once per rotate gesture (on release, only if the angle actually changed), payload `{ roomId, type, rotation }` with the final angle as a full-precision float, not rounded to a step.
- **Design snapshot**: `rotation` flows through `POST /api/designs`' `rooms` payload (validated server-side via a new `isRotationDegrees` check in `shared/contract.js`) and persists in `dreamhome.designs.snapshot`. The reveal card's mini floorplan renders it too (it reuses `RoomArt` directly), so a rotated room shows rotated there as well — not required by this phase's ACs, but free, since rotation lives on the room object `RoomArt` already receives.

## 2. Contract diff

- `EVENT_TYPES`: added `room_rotated`.
- `validateDesignRoomEntry`: added an optional `rotation` field, validated as a finite number in `[0, 360)` (a plain range check, not `isNonNegativeInt` — rotation is a free angle, not a step count).
- `GET /api/catalog`'s `rooms[]` entries lost four fields: `minW`, `minH`, `maxW`, `maxH`. Nothing in the client reads them anymore (grepped clean after the change).

## 4. Open issues / known-broken

- **Collision approach — full SAT was implemented, not the bounding-box fallback the phase prompt allowed.** Flagging this explicitly per the phase prompt's instruction to document the trade-off either way: two rectangles have only 2 unique edge-normal axes each (opposite edges are parallel), so a full rect-vs-rect SAT test is 4 axis projections total — small enough that there was no real size/complexity reason to fall back to the documented bounding-box approximation. See Decisions below for the one case where this matters concretely.
- **Elevation view uses each room's axis-aligned `x/y/w/h`, not its rotated shape — as directed by the phase prompt, and already true by construction.** A room's grid position and footprint (`x`, `y`, `w`, `h`) never change when it's rotated; rotation is purely a rendering transform layered on top in `RoomArt.jsx`. `ElevationView.jsx`'s floor-width calculation was already reading `x`/`w` directly (Phase 7), so it was already using the "axis-aligned bounding box" the phase prompt asked for — no code change was needed there, only this note. The real, documented limitation: a heavily-rotated room's true visual footprint (which can extend past its nominal grid cells — see the next item) is invisible to the elevation view, which only ever sees the unrotated `w`. A player who rotates a room 45° and fills the visual gap that opens up around it won't see that reflected in the elevation's floor width.
- **A rotated room's drawn art can visually extend past its own grid footprint.** A square room rotated 45° reaches out to its diagonal (~41% further than its flat edge) — `RoomArt.jsx`'s `<svg>` now sets `overflow: 'visible'` so that bleed isn't clipped mid-rotation (clipping it would cut off corners at exactly the angles AC2 asks to screenshot). This is deliberate, not a leak: the room's actual collision shape (via SAT) matches what's drawn, corner-for-corner, so a neighbor being visually "reached into" is always also correctly blocked by collision — nothing about this lets a rotated room's *art* claim space its *collision* doesn't also claim. But it does mean two rooms can appear to visually overlap by a sliver at their rotated corners' anti-aliased edges in some viewing conditions, which is a rendering nicety, not a collision bug.
- **The selection boxShadow ring, drag-move preview overlay, and both handles stay axis-aligned regardless of the room's rotation.** This is intentional for the handles (see Decisions), but means the gold selection ring doesn't hug a rotated room's actual silhouette, and the dashed preview shown while *moving* a rotated room is its unrotated bounding box, not its true rotated shape. Neither affects correctness (the real SAT check still governs whether a move succeeds), only how tightly the visual feedback tracks the room's true shape.
- **No mobile-friendly rotate stepper.** Phase 6 added a `ResizeStepper` (+/- buttons) as a touch fallback for the resize handle, which is a real drag target too small to hit precisely on touch. The rotate handle has the exact same problem and no equivalent fallback was built this phase — out of scope for what was asked, but the same class of gap Phase 6 closed for resize.
- Carried forward, still open (Phase 4/5/6/7): `catalog_listings` placeholder data, no auth on `/sales.html`/`/api/sales/leads`, `dreamhome.events` same-millisecond ordering assumption, no monitoring/error tracking, balcony not shown as a facade feature on the elevation view.

## 5. Decisions and why

- **Real SAT collision, not the documented bounding-box fallback.** The phase prompt explicitly allowed substituting each room's rotated bounding box for collision if full polygon intersection proved too large for this phase. It didn't — a rectangle-vs-rectangle SAT test only ever needs 4 axis projections (2 unique edge normals per rectangle), which is a compact, well-understood, easily-unit-tested piece of geometry (`client/src/lib/grid.js`'s `rectCorners`/`rectAxes`/`project`/`rectsIntersect`). The bounding-box fallback would have been *more* conservative than necessary in exactly the cases that make rotation interesting: a room rotated 45° has a bounding box (its own diagonal, ~41% larger than its flat footprint) that would falsely block plenty of placements a real player would expect to fit, since the true rotated shape doesn't occupy that whole square. Implemented and unit-tested directly (see Verification) before wiring into the UI, so this wasn't a risky last-minute swap.
- **Rotation is set from the cursor's absolute angle around the room's center, not a relative delta.** Dragging the handle makes the room's angle track the cursor directly — grab any point on the circle the handle sweeps and the room points there. A delta-based scheme (accumulating relative movement) is more common in some editors but feels laggy/indirect for a single circular handle with an obvious "up = 0°" rest position; absolute-angle tracking is the more direct, discoverable interaction for exactly this handle shape.
- **The rotate handle (and resize handle, and the selection ring) live outside `RoomArt`'s rotation transform.** They're rendered by `RoomBlock.jsx`, a sibling of the rotating `<g>`, not a child of it. If the handles rotated with the room, the rotate handle would chase its own tail — dragging it would need to account for its own already-rotated position, which is a much harder interaction to reason about (and to use) than "the handle always starts straight up from center, drag it anywhere on the circle." Keeping handles unrotated matches how the existing resize handle already worked (Phases 2-7) and needed no special-casing to preserve.
- **Rotation is only rejected at the point it would cause a collision, not disabled pre-emptively.** While dragging the rotate handle, each intermediate angle is collision-checked the same way resize already was (Phases 2-7's `collides()` gate before `setPlaced`) — if the candidate angle would overlap a neighbor, that frame's update is simply skipped, freezing the room at its last valid angle until the cursor sweeps back to a clear angle. This reuses the exact skip-if-invalid pattern the resize handle already established, rather than inventing a new interaction model for rotation.
- **`overflow: visible` on `RoomArt`'s `<svg>`, not a larger SVG canvas.** A rotated room's content can reach outside its nominal `W`×`H` box (see Open Issues). The alternative — enlarging the SVG to `Math.hypot(W, H)` and re-centering — would require every furniture/texture coordinate in `RoomArt.jsx` to account for a variable offset, exactly the per-drawing-code change the phase prompt asked to avoid ("individual furniture/wall/texture code doesn't need to change, only the outer transform"). `overflow: visible` achieves the same visual result — nothing gets clipped mid-rotation — with a one-line change.

## 6. Verification

1. **Freeform resize past the old bounds, cost scaling correctly at both extremes (AC1)** — a Living Room (old bounds: 2×2 to 6×5 cells) was dragged via its resize handle to 12×7 cells (24×14m), filling most of the 14×10 plot; its label read `KES 29.5M`, matching `12 × 7 × 260,000 × 1.35 (Polished Porcelain) = 29,484,000` exactly, and the ticker read `KES 33.0M` (`29.5M room + 3.5M shell`) — the resize also correctly re-triggered the existing Phase 3 financing-modal logic at the 18M threshold, unprompted, confirming nothing in that unrelated path broke. The same room was then dragged down to 1×1 cell (2×2m, the new universal floor), label `KES 351K` (`1 × 1 × 260,000 × 1.35`), rendering with no furniture (below its `W > 60 && H > 55` threshold, same graceful-degradation logic Phase 3 shipped, unchanged) but a clean floor/wall/door render — no errors either direction. Screenshots taken at both extremes.
2. **Rotation through 0°/45°/180°, furniture/walls/texture rotating as one unit (AC2)** — a Living Room was rotated via the handle to 47.1° and 178.8° (read directly from the live `<g transform="rotate(...)">` attribute). At 47° the room renders as a clean diamond: wall outline, both window notches, sofa, and coffee table all rotated together with continuous, unbroken edges — no seam between "rotated" and "unrotated" parts, because there are none (everything is inside the one transformed `<g>`). At 179° the room is a correctly-flipped square (door arc and windows now on the opposite edges from their 0° positions). Both handles and the gold selection ring stayed fixed at the room's unrotated position throughout, as designed. Screenshots taken at ~0°, ~47°, and ~179°.
3. **Rotated rooms correctly block each other, verified both as a unit test and live in the app (AC3)** — three independent checks: (a) a standalone Node script against the real `collides()` function showed a 4×4 room rotated 45° blocking a candidate placement that its *unrotated* bounding box would have allowed through (`collides(4, 0, 3, 3, ...)` → `false` at rotation 0, `true` at rotation 45 — the same candidate, only the neighbor's rotation differs), proving this is true rotated-rectangle intersection, not a bounding-box comparison; (b) live in the app, a Living Room placed exactly touching a Kitchen (zero gap) was selected and its rotate handle dragged — rotation stayed pinned at 0° for the entire gesture (any non-zero angle immediately overlaps a neighbor with zero clearance, so every candidate angle was correctly rejected — the "deliberate overlap attempt that gets rejected"); (c) the same Kitchen moved to open a ~1-cell gap, then the same rotate gesture reached 100.8° cleanly with no rejection (the "near-miss that succeeds" — enough clearance for the full swing) — screenshotted, showing the rotated Living Room sitting flush beside the Kitchen with no overlap.
4. **A rotated room in a finished design doesn't break the elevation view (AC4)** — the two-room design from the previous check (Living Room at 100.8°, Kitchen at 0°) was submitted via "Finish my design." `POST /api/designs` returned `201`; the reveal card rendered both the front elevation (a normal one-floor, flat-roof Modern Minimalist house — unaffected, since it only ever reads unrotated `x/y/w/h`, per the Decisions above) and the mini floorplan, which additionally rendered the Living Room as a visibly rotated parallelogram (a bonus, not required by this AC, confirming rotation flows cleanly through the whole snapshot → reveal pipeline). No errors either component.
5. **`room_rotated` lands in `dreamhome.events` with the final angle (AC5)** — queried `dreamhome.events` directly after the test sessions above: four `room_rotated` rows, each `payload.rotation` matching the exact angle read from the live DOM at the moment of release (e.g. `100.81573156596598`, `178.81357061904964`) — full float precision preserved end to end, not rounded to a step. The corresponding `dreamhome.designs.snapshot.rooms[0].rotation` for the finished design also matched (`100.81573156596596`), confirming the same value reached both the event log and the design snapshot.

## 7. Next-phase entry points

No further phases are defined in `docs/phases/PROMPTS.md`; this phase was scoped directly by the user, same as Phase 7. Candidate follow-ups, none currently requested:

- A mobile-friendly rotate stepper, mirroring Phase 6's `ResizeStepper`, for the same reason it was needed there (the rotate handle is a real drag target, too small to hit precisely on touch).
