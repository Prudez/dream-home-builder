# Phase 9 Handoff

> Repo path: `docs/phases/phase-9.md`.
> Companion: `shared/contract.js` holds the current interface shape. This document references it; it does not duplicate it.

**Phase:** 9
**Date closed:** 2026-08-05
**One-line summary:** Toggleable furniture add-ons (rug, TV console, headboard, bar stools, and similar flourish pieces) layered on top of the existing base furniture tier — independently priced, independently rendered, independently toggled per room, with a new `addon_toggled` event and a "detail-oriented" engagement signal for players who switch on 3+ in one room.

---

## 1. What shipped

- **`catalog_furniture_addons` table** (migration `008_furniture_addons.sql`): `room_type`, `addon_key`, `name`, `price`, `sort_order`, unique on `(room_type, addon_key)`. Seeded with 1-4 add-ons for every room type that already had a `catalog_furniture` entry — `living` (rug, TV console, wall art, plant), `bedroom`/`master` (headboard, bedside lamp, rug, foot-of-bed bench — priced separately per type), `kitchen` (bar stools, pendant light), `bath` (bath mat, wall shelf), `office` (desk lamp, wall art), `veranda`/`garden` (planters, string lights), `pool` (umbrella), `dsq` (wall shelf, curtains), `balcony` (planters, string lights). 27 rows total.
- **Independent of the base tier**: a room's `furnitureId` (Essentials / Family Lounge / etc.) and its `addons` array (new field on placed rooms, default `[]`) are separate concerns end to end — separate catalog table, separate cost term, separate contract field, separate event. A room can sit on the free "Essentials" tier with every add-on switched on, or the top tier with none.
- **Cost math**: `shared/cost.js` gained `resolveAddons`/`addonsCost`, and `roomCost`/`totalCost` both take an optional `addonsByType` map (default `{}`, so every existing call site kept working during the refactor) and add each enabled add-on's price on top of the room's base + finish + furniture cost. Used identically client-side (live ticker) and server-side (`POST /api/designs`' recompute, `server/lib/replay.js`'s peak-cost tracking) — the same shared function, no duplicated math.
- **Picker UI**: the Furniture tab in `Picker.jsx` keeps its existing tier cards unchanged, with a new "Add-ons" checklist rendered directly below them — one row per add-on, name + price (`+KES Nk` or `included`), a real `<input type="checkbox">` reflecting `room.addons.includes(addonKey)`. Only rendered for room types that have add-on rows (`hasAddons`), and the Furniture tab itself now also appears for a room type that has add-ons even without a furniture tier (defensive; doesn't occur in the current catalog since every add-on room type also has furniture).
- **Rendering**: `RoomArt.jsx` gained `drawAddons(type, W, H, addons)`, structurally parallel to the existing `drawFurniture()` — one `if (type === ...)` block per room type, each add-on gated on `addons.includes(key)` plus its own minimum-size threshold so it degrades gracefully at very small room sizes, the same convention `drawFurniture` already used. Drawn as a second `<g>` alongside the existing furniture `<g>`, inside the same rotation transform from Phase 8 — an add-on rotates with the room like everything else RoomArt draws.
- **`addon_toggled` event**: added to `EVENT_TYPES`. Logged once per checkbox click from `PlotCanvas.jsx`'s new `handleToggleAddon`, payload `{ roomId, type, addonKey, on, addonPrice, resultingRoomCost }` — `on` and `resultingRoomCost` are the *new* state (same convention as `room_resized`/`room_rotated`: log what changed to, not a delta), so the event alone tells the full story without needing a replay to see the price impact.
- **`server/lib/replay.js`**: tracks each room's `addons` array across its reconstructed session history (starts `[]` on `room_added`, updated by `addon_toggled`), so peak-cost tracking (used for the budget-band signal) reflects add-on spend at whatever point it peaked, even if a player later toggles add-ons back off — consistent with the project's existing "peak cost matters even after rooms are removed" principle.
- **Detail-oriented / engagement signal**: `server/lib/signals.js` finds the room (if any) with 3+ enabled add-ons in the final design snapshot, and pushes a `detail_oriented` signal naming the room and its add-ons (e.g. `"Accent Rug, TV Console, Wall Art on Living Room → detail-oriented, high engagement"`). Read from the final snapshot's `rooms[].addons`, the same "current state" pattern already used for `splurge_rooms`/`palette_taste`/lifestyle flags — not a session replay, since add-on toggling doesn't need to survive later removal the way peak-cost does. It also counts toward `lifestyleFlagCount` in the lead score (capped at 15 across all lifestyle flags), the same as the entertainer/pool-loungers/bathtub/DSQ/executive-study flags it sits alongside.

## 4. Open issues / known-broken

- **Addon catalog covers every room type that had a furniture entry, per the phase instruction — but list length and exact items were a judgement call**, not specified beyond the six examples the user gave (bedroom, living, kitchen, bathroom, garden, pool). The remaining five types (`master`, `office`, `veranda`, `dsq`, `balcony`) got sensibly analogous 1-2 item lists (e.g. balcony/veranda both got planters + string lights, mirroring garden) rather than anything the user explicitly asked for. Easy to retune in the catalog table alone if sales wants different items or prices — no code change needed.
- **No mobile-specific affordance for the checklist.** The checkboxes are real `<input type="checkbox">` elements at a comfortable tap size inside a 44px-min-height row (consistent with Phase 6's touch-target pass), but no dedicated mobile layout was built beyond that — it wasn't needed; the checklist already stacks vertically and scrolls with the rest of the Picker panel on narrow screens.
- **The `detail_oriented` signal is computed from the final design snapshot, not a session replay** — a player who toggles 3+ add-ons on a room and then removes that room entirely before finishing won't trigger it, the same way `splurge_rooms`/`palette_taste`/other "current state" signals already work. This is a deliberate consistency choice (see Decisions), not an oversight, but is worth naming since the *cumulative* signals elsewhere in this same function (peak cost, upgrades) do survive removal.
- Carried forward, still open (Phase 4-8): `catalog_listings` placeholder data, no auth on `/sales.html`/`/api/sales/leads`, `dreamhome.events` same-millisecond ordering assumption, no monitoring/error tracking, balcony not shown as a facade feature on the elevation view, no mobile-friendly rotate stepper (Phase 8), elevation view's axis-aligned-bbox approximation for rotated rooms (Phase 8).

## 5. Decisions and why

- **Add-ons are a separate catalog table and a separate room field, not folded into `catalog_furniture`/`furnitureId`.** The base tier is a single mutually-exclusive choice (a room has exactly one `furnitureId`); add-ons are independent toggles (a room has zero or more). Modeling both as rows in the same table would have needed a `kind` discriminator and different selection semantics in every place that reads it (Picker, cost math, rendering, replay) — a second table with a plural array field on the room is the direct shape for "independent of tier," matching the phase instruction exactly rather than approximating it inside the existing single-select model.
- **`resultingRoomCost` in the event payload, not just the add-on's own price.** Every other cost-affecting event in this project (`room_resized`, `furniture_changed`) logs the *new* value of what changed, not a delta, so a later reader never needs to replay history to know "what did this look like right after." `addon_toggled` follows the same convention: `on` is the new toggle state, `resultingRoomCost` is the room's new total. `addonPrice` is included too, purely as a convenience so a reader doesn't need the catalog just to see what a single add-on costs.
- **The detail-oriented signal reads the final snapshot, matching `splurge_rooms`/`palette_taste`, not `replaySession`'s cumulative counters.** The signals function already draws a clear line between "current state" signals (what the finished design looks like) and "cumulative" signals (what happened over the whole session, surviving later undo). Whether a player is "detail-oriented" is naturally about what they actually shipped, not a moment that passed and was undone — the same reasoning that already put `splurge_rooms` and lifestyle flags on the current-state side of that line.
- **Add-ons render as their own `<g>`, structurally separate from `drawFurniture`'s `<g>`, both inside the same Phase 8 rotation transform.** Keeping `drawAddons` as its own function (rather than interleaving add-on branches into `drawFurniture`) keeps the "tier" and "add-on" concerns visually separable in the code the same way they're separable in the data model, and means neither function needs to know about the other's gating logic (tier index vs. array membership).

## 6. Verification

1. **Every room type with add-ons shows its checklist correctly, only when selected, reflecting live in the render (AC1)** — placed a Living Room and a Kitchen. Selecting the Living Room's Furniture tab showed its own four-item checklist (Accent Rug +KES 35K, TV Console +KES 85K, Wall Art +KES 40K, Statement Plant +KES 18K); selecting the Kitchen showed a completely different two-item checklist (Bar Stools +KES 55K, Pendant Light +KES 32K) — confirming per-room-type scoping, not a shared list. Checking Accent Rug, TV Console, and Wall Art on the Living Room immediately drew a rug rectangle, a dark TV-console bar, and a wall-art square on the live SVG (screenshotted, zoomed) with no page reload or delay. Checking Bar Stools and Pendant Light on the Kitchen immediately drew two stool circles and a pendant circle. All 11 room types with add-on rows were confirmed present via a direct `GET /api/catalog` check (`furnitureAddons`: 27 rows across `living, bedroom, master, kitchen, bath, office, veranda, garden, pool, dsq, balcony`); two representative types were walked through live in the browser as above.
2. **Price ticker updates correctly, matching a hand-calculated example (AC2)** — the Living Room (3×3 cells, Modern Minimalist's default Polished Porcelain finish, ×1.35 mult, Essentials furniture tier at KES 0): base room cost `round(260,000 × 9 × 1.35) = 3,159,000`. Ticker read **KES 6.7M** before any add-ons (`3,500,000` shell + `3,159,000` room = `6,659,000`, displays rounded to one decimal in millions). Checking Accent Rug (+35,000) → room cost `3,194,000`, ticker still displayed `6.7M` (still rounds to the same tenth); checking TV Console (+85,000) then Wall Art (+40,000) brought the room to `3,319,000` and the ticker to **KES 6.8M** (`6,819,000` total) — matching the hand-calculated sum exactly. Confirmed independently via the `addon_toggled` events' own `resultingRoomCost` field logged to `dreamhome.events` (see next item): `3,194,000` → `3,279,000` → `3,319,000`, each exactly base + the running add-on sum.
3. **`addon_toggled` events land correctly in `dreamhome.events`, in order (AC3)** — queried `dreamhome.events` for the test session directly:
   ```
   addon_toggled {"on":true,"type":"living","roomId":1,"addonKey":"rug","addonPrice":35000,"resultingRoomCost":3194000}
   addon_toggled {"on":true,"type":"living","roomId":1,"addonKey":"tv_console","addonPrice":85000,"resultingRoomCost":3279000}
   addon_toggled {"on":true,"type":"living","roomId":1,"addonKey":"wall_art","addonPrice":40000,"resultingRoomCost":3319000}
   ```
   Three rows, in the exact order the checkboxes were clicked, each `created_at` timestamp increasing, each `resultingRoomCost` matching the hand-calc in the previous check.
4. **A session with 3+ add-ons on one room shows the engagement signal in `lead_signals` (AC4)** — with Accent Rug, TV Console, and Wall Art enabled on the Living Room, the design was finished and a lead submitted via WhatsApp. `dreamhome.lead_signals` for that session's row includes:
   ```json
   { "key": "detail_oriented", "label": "Engagement signal",
     "value": "Accent Rug, TV Console, Wall Art on Living Room → detail-oriented, high engagement" }
   ```
   alongside the expected `style_segment`/`build_ambition`/`budget_band`/`finish_expectation` signals, and `lead_score: 10` (5 points for the entry-level budget band + 5 points for the one lifestyle flag — the detail-oriented signal — matching the documented score breakdown in `signals.js`).
5. **Toggling all add-ons off returns the room to its base-tier appearance and price with no leftover artifacts (AC5)** — with all three Living Room add-ons enabled (ticker `KES 6.8M`, rug/TV-console/wall-art all visibly drawn), unchecking all three brought the ticker back to **KES 6.7M** exactly, and a zoomed screenshot of the room showed only the base Essentials furniture (sofa bar, coffee table circle) with no rug, TV console, or wall-art shapes remaining — pixel-identical to the room's appearance before any add-on was ever checked. This works by construction, not special-casing: `RoomArt` rebuilds its `els` array from scratch on every render from the room's current `addons` array, so there's no stale-element state to clean up.
