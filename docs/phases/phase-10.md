# Phase 10 Handoff

> Repo path: `docs/phases/phase-10.md`.
> Companion: `shared/contract.js` holds the current interface shape. This document references it; it does not duplicate it.

**Phase:** 10
**Date closed:** 2026-08-05
**One-line summary:** Room rendering refactored from one hardcoded path into a pluggable style-renderer interface (`client/src/lib/roomStyles/`), with the original rendering reorganized as the first style ("Soft Depth") and a complete second style ("Line Art" — bold navy outlines, material colour-coding, proportion-correct furniture) built against the same interface, switchable live via an always-visible switcher near the canvas.

---

## 1. What shipped

- **The style-renderer interface** (`client/src/lib/roomStyles/index.js`, fully documented there): six hooks — `drawFloor`, `drawPool`, `drawGarden`, `drawFurniture`, `drawAddons`, `drawWalls` — each a plain function taking a context object and returning an array of SVG children. Any style module implementing all six is a complete, swappable visual language. The registry (`ROOM_STYLES`, `STYLE_LIST`, `DEFAULT_STYLE_KEY`, `getStyle()`) is the single place a new style gets wired in.
- **`RoomArt.jsx` is now a thin dispatcher**: it resolves the room's pixel size and colour, builds the shared context object, calls `getStyle(styleKey)` once, and routes to `drawPool`/`drawGarden`/`drawFloor` (by `roomDef.groupName`) then `drawFurniture` + `drawAddons` then `drawWalls`, in that fixed order — the same z-order the single-style renderer always used (floor first, furniture/addons above it, walls last so wall lines stay crisp over furniture near an edge). Rotation (Phase 8) and the outer `<svg>` stay entirely in RoomArt, style-independent — no style module ever touches either.
- **"Soft Depth"** (`roomStyles/softDepth.js`): the project's original rendering (Phases 1-9), reorganized into the six hooks with no visual changes — every shape, coordinate, and colour is identical to pre-Phase-10 `RoomArt.jsx`, just relocated. This was a wrap, not a rebuild, per the phase brief.
- **"Line Art"** (`roomStyles/lineArt.js`): a complete second style built from scratch against the same interface. Bold `#0A1E3C` (navy) outlines (1.25-2px depending on piece size) around every furniture shape and wall. Material colour-coding: `#13315C` navy for soft seating/upholstery (sofas, armchairs, office chairs, bar stools), `#E3D5BE`/`#F2EAD9` cream for bedding surfaces (mattresses, pillows, pool loungers — anything lain-on), `#8E5B33` wood for hard furniture (bed frames, headboards, wardrobes, desks, kitchen counters/cabinets, TV consoles), `#C9A14A`/`#A97F2C` gold for accent pieces (coffee/dining tables, kitchen islands, lamps, pendant lights, umbrellas). Rugs (both the base-tier living-room rug and every Phase 9 rug/bath-mat addon) render as a shared dashed-outline rounded rect, drawn beneath the piece that sits on it. Beds and pool loungers use a narrower, taller ("portrait") rectangle than the original — deliberately not the same wide-shallow silhouette as seating, per the phase brief's proportion rule. Floor textures (tile/plank/parquet/gloss/carpet/granite), garden (grass/trees/landscaping/lawn flowers), pool (water/deck/ladder/ripples), and every no-finish utility room (gate/borehole/garage) are all re-rendered in the same navy-outline language, not left in the old style.
- **Style switcher**: a small, always-visible `STYLE_LIST`-driven pill switcher in `PlotCanvas.jsx`, positioned above the floor tabs — visible regardless of floor count, selection state, or player progress. Deliberately not part of `ShellStage` or any other design choice, since it's a pure rendering preference.
- **`style_changed` event**: added to `EVENT_TYPES`, logged once per switch from `App.jsx`'s `handleStyleChange` with payload `{ styleKey }` (the new value, same "log what changed to" convention as `room_resized`/`room_rotated`/`addon_toggled`).
- **State ownership**: `App.jsx` owns `styleKey` (`useState(DEFAULT_STYLE_KEY)`), passed down to both `PlotCanvas` (which owns the switcher UI and calls back up via `onStyleChange`) and `RevealCard` (so the reveal card's mini floorplan renders in whatever style was active when the player finished). It is never sent to the server as part of a room or design — the design snapshot (`rooms[]`) carries zero style information, matching the phase brief's framing that style changes "only how those selections are drawn," never the underlying data.

## 4. Open issues / known-broken

- **A `console.error` "Received NaN for the cx/cy attribute" was observed once during interactive testing** (a single timestamp, both `cx` and `cy` flagged together — consistent with one circle/ellipse element). It did not reproduce across repeated, deliberate attempts afterward: placing rooms fresh in both styles, switching styles rapidly (8 toggles), resizing, and rotating, all with the browser console open and clean throughout. It also never corresponded to any visible rendering artifact in any of the ~20 screenshots taken during verification — every room rendered correctly in every style at every point. The most likely explanation is this session's browser-automation workaround (hand-dispatched `PointerEvent` sequences, documented since Phase 7/8, occasionally recovered from a CDP timeout by dispatching a standalone `pointerup` separately from its `pointerdown`/`pointermove` sequence) producing a single inconsistent intermediate frame in dnd-kit's translated-rect calculation, not a defect in the app's rendering logic under normal user interaction. Flagged here rather than silently dropped, per this phase's instruction to surface genuinely uncertain findings rather than omit them. Worth a quick recheck early in Phase 11 if it recurs.
- **Line Art's exact shapes are an original illustration, not a pixel-for-pixel spec.** The phase brief gave a visual language (outline weight, colour roles, rug treatment, seating-vs-lain-on proportions) rather than exact coordinates, so every piece in `lineArt.js` was drawn fresh to follow that language while staying structurally parallel to `softDepth.js` (same room-type branches, same size thresholds for graceful degradation at small room sizes). Reasonable, but a designer reviewing the actual pixel output may want adjustments — cheap to make since every shape lives in one well-organized file.
- **No dedicated mobile treatment for the style switcher.** It's a normal button row that wraps at narrow widths (`flexWrap: 'wrap'`), consistent with the Phase 6 touch-target pass, but wasn't screenshotted at 375px this phase.
- Carried forward, still open (Phase 4-9): `catalog_listings` placeholder data, no auth on `/sales.html`/`/api/sales/leads`, `dreamhome.events` same-millisecond ordering assumption, no monitoring/error tracking, balcony not shown as a facade feature on the elevation view, no mobile-friendly rotate stepper (Phase 8), elevation view's axis-aligned-bbox approximation for rotated rooms (Phase 8), Phase 9's add-on catalog covering some room types by judgement call rather than explicit spec.

## 5. Decisions and why — including the interface shape, for Phase 11

- **The interface has six hooks, not the four-or-so the phase brief's "e.g." list implied, because pool and garden are structurally different from a textured floor, not a variation on one.** The brief's example list (`drawWalls`, `drawFloor(finishKey, colorKey)`, `drawFurniturePiece(pieceKey, tier, addons)`, `drawGarden(finishKey)`, `drawPool(finishKey)`) was illustrative, not a mandated signature — confirmed by rereading it as "e.g." Splitting `drawPool`/`drawGarden` out from `drawFloor` (rather than branching inside one mega-hook, which is what the original code did) keeps each hook's job single-purpose and directly mirrors the room-type dispatch RoomArt already needed to do (`roomDef.groupName === 'pool' | 'garden' | else`). **For Phase 11 (Bold Icon, per the brief): implement all six hooks in a new `roomStyles/boldIcon.jsx`, add it to `STYLE_LIST` in `index.js`, and nothing else needs to change** — RoomArt, the switcher, RevealCard, and the event logging are all already style-count-agnostic.
- **`drawFurniture` stayed one function per room type (keyed by `type`), not split into a `drawFurniturePiece(pieceKey, ...)` called once per individual piece (sofa, table, rug, ...).** The brief's example name suggested a more granular per-piece abstraction. A fully piece-based system is a plausible future direction (and would let, say, a "rug" or "lamp" piece share one implementation across room types instead of being redrawn per type as it is now in both styles), but building it for *this* phase's first style would have meant rewriting Soft Depth's logic instead of relocating it — directly against the phase brief's explicit instruction that Soft Depth "should be a wrap/reorganize of current code, not a rebuild." The current interface is not a dead end for this: a future style (or a Phase-12-style refactor) could introduce a `drawPiece(pieceKey, ctx)` seventh hook without touching the other five or breaking Soft Depth/Line Art, since RoomArt only ever calls hooks that exist on the active style object.
- **Style is never sent to the server or stored in a design snapshot.** The phase brief frames switching styles as changing "only how those selections are drawn" — the room/finish/furniture/addon data is the durable record; the style is a viewing preference, ephemeral to the session, the same category as which floor tab is currently active. Persisting it would have meant a contract/schema change for a value that only ever needs to survive as long as the browser tab does. `style_changed` is still logged to `dreamhome.events` (AC4), so sales analytics can see which style players prefer without the design data itself carrying a style field.
- **The switcher lives in `PlotCanvas.jsx`, but the `styleKey` state lives in `App.jsx`.** `RevealCard` needs the same value PlotCanvas's switcher controls (so the mini floorplan matches what the player was just looking at), and `RevealCard` is a sibling of `PlotCanvas` under `App`, not a descendant — so the value has to live at the common ancestor. This is the same lifting pattern the project already uses for `session`/`shell`/`design`.
- **Rugs share one shape (dashed-outline rounded rect) across every occurrence in Line Art** — the base-tier living-room rug, all three bedroom/master rug variants, and the bath mat addon all call the same local `rug()` helper in `lineArt.js`. The phase brief specified this treatment once, generically ("rugs shown as..."), so treating it as one shared visual rule applied everywhere a rug-like surface appears (rather than one-off styling per occurrence) is both more consistent and less code.

## 6. Verification

1. **Every existing room type renders correctly in both styles, including finish variants and both furniture tiers/add-ons (AC1)** — a 9-room, 2-floor (Maisonette, Classic Stone pack) design was built covering Living Room, Kitchen, Bedroom, Bathroom, Master En-suite (×2), Home Office, Garden, and Swimming Pool. Kitchen was set to the "Breakfast Nook" tier with both Bar Stools and Pendant Light add-ons enabled; Pool was set to "Infinity Edge" finish, "Loungers" tier, and the Pool Umbrella add-on. The entire layout was screenshotted in Soft Depth, then the style switcher was clicked to Line Art and the identical layout re-screenshotted — living room (sofa/table), bedroom (portrait bed), bathroom (WC/shower), master en-suite (bed/wardrobe), kitchen (counter/hobs/sink/bar stools/pendant light), and home office (desk/chair) all confirmed rendering correctly and distinctly in both styles, well beyond the required 6 combinations.
2. **Garden and pool render correctly in both styles, with a finish variant each (AC2)** — Garden (Lawn finish, with its characteristic flower speckles) and Pool (Infinity Edge finish, with loungers and umbrella) were both screenshotted in Soft Depth (gradient water, grass texture) and Line Art (navy-outlined water and grass fill, cream portrait loungers, gold umbrella, navy ladder icon) — zoomed screenshots confirmed clean, correct rendering in both.
3. **Switching styles live re-renders the same layout with no data loss (AC3)** — the 9-room design's cost ticker read **KES 23.0M** and "7 rooms" (at that point in the build) immediately before switching to Line Art, and **KES 23.0M**/"7 rooms" immediately after, with every room in the exact same grid position, size, finish, and furniture/add-on selection — only the drawn style changed. (Room count later grew to 9 as Kitchen and Home Office were added, independently of the style switch itself.)
4. **A `style_changed` event lands correctly in `dreamhome.events` (AC4)** — queried directly after the Soft Depth → Line Art switch above: `style_changed {"styleKey":"line-art"}`, timestamped correctly within the session's event stream.
5. **The elevation view and reveal card work correctly regardless of active style (AC5)** — with Line Art active, "Finish my design" was submitted; the reveal card's front elevation (a two-storey Classic Stone house with a gable roof) rendered correctly and identically to how it always has — expected, since `ElevationView.jsx` never calls `RoomArt` or reads `styleKey` at all, it only reads room `x`/`y`/`w`/`h`/type counts. The reveal card's mini top-down floorplan, which *does* call `RoomArt`, correctly rendered every room in Line Art (navy sofa icon, wood-toned kitchen/bed rects, navy-outlined pool, green garden circle) — confirming `styleKey` flows cleanly through to the reveal stage.

## 7. Next-phase entry points

- Add `client/src/lib/roomStyles/boldIcon.jsx` implementing all six interface hooks (`drawFloor`, `drawPool`, `drawGarden`, `drawFurniture`, `drawAddons`, `drawWalls`).
- Add it to `STYLE_LIST` in `roomStyles/index.js`. The switcher UI, `RoomArt`'s dispatch, `RevealCard`, and `style_changed` logging all already support an arbitrary number of styles — none of them need to change.
- Other candidates, none currently requested: screenshot the style switcher at 375px for the mobile pass; consider a `drawPiece(pieceKey, ctx)` seventh hook if a future style wants shared cross-room-type piece rendering (e.g., one "rug" implementation instead of each style redefining it per room type, as both Soft Depth and Line Art currently do); feed the player's most-used style into a lead signal if sales wants that data point.
