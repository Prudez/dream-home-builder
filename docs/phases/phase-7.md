# Phase 7 Handoff

> Repo path: `docs/phases/phase-7.md`.
> Companion: `shared/contract.js` holds the current interface shape. This document references it; it does not duplicate it.

**Phase:** 7
**Date closed:** 2026-08-04
**One-line summary:** A new Balcony room type (upper-floors-only, finishes, furniture, RoomArt rendering, a lifestyle signal) and a front-elevation SVG render on the reveal card, derived from the actual placed rooms and the chosen style pack's roof shape.

---

## 1. What shipped

- **Balcony room type**: `dreamhome.catalog_rooms` gained an `upper_only` boolean (the inverse of the existing `ground_only`) and a `balcony` row (min 2x1, max 4x2, default 3x1). Unlike `ground_only` rooms, which stay visible-but-disabled on the wrong floor, `upperOnly` rooms are filtered out of the palette entirely on the ground floor (`Palette.jsx`) — the phase prompt's AC1 asked for "absent," not "disabled," and a balcony can never legally exist on the ground floor, so offering it there even greyed out would be misleading.
- **Balcony finishes**: new `balcony` finish group in `catalog_finishes` — Tiled Deck (`tile` texture, standard), Glass Balustrade (`gloss` texture, +25%), Timber Decking (`plank` texture, +15%), each with 2-3 colourways, reusing the existing texture-rendering branches in `RoomArt.jsx` (no new texture code needed).
- **Balcony furniture**: `catalog_furniture` gained `Railing` (included, tier 0) and `Balcony Lounge` (small table, chairs, planters, +KES 140K, tier 1), following the veranda furniture pattern.
- **RoomArt rendering**: a balustrade (border rect + baluster posts along the top edge) is drawn for every balcony regardless of furniture tier, representing the always-present "Railing." `drawFurniture` gained a `balcony` case for tier 1 (table, two chairs, two planters). Balconies are non-indoor (`roomDef.indoor = false`, like verandas), so no wall/window is drawn for them.
- **Lifestyle signal**: `computeLeadSignals` (`server/lib/signals.js`) gained an `outdoor_priority` signal ("Balcony placed → outdoor space priority") whenever a balcony is present in the design snapshot. See Decisions below for why this is a signal only, not a lead-score input.
- **Front elevation**: new `client/src/components/ElevationView.jsx`, a standalone SVG component (not a modification of `PlotCanvas.jsx`'s per-floor top-down canvas). It derives each floor's footprint width from the actual placed rooms' grid x-extent on that floor, stacks floors bottom-up centered on the widest floor, draws a roof shaped by the style pack (flat parapet for Modern Minimalist/Smart Compact, hip for Swahili Coastal, pitched gable for Classic Stone), draws a window row per floor sized to that floor's bedroom+master count (minimum 1, so an all-common-room floor isn't a blank wall), and a door on the ground floor. Wired into `RevealCard.jsx` above the existing mini floorplan, using the style pack's first swatch colour as the facade colour.

## 2. Contract diff

No changes to `shared/contract.js` (no new endpoints or event types — balcony placement/resize/finish/furniture reuse the existing `room_added`/`room_resized`/`finish_changed`/`furniture_changed` event types and `POST /api/designs` room shape unchanged). One additive catalog response field: `GET /api/catalog`'s `rooms[].upperOnly` (boolean), parallel to the existing `groundOnly`.

This does not indicate an app bug; the palette-to-canvas drag path is unchanged from Phases 2-6, and AC1's balcony palette visibility (which needed no drag, only floor-tab clicks) verified cleanly through the same browser.
- Carried forward, still open (Phase 4/5/6): `catalog_listings` placeholder data, no auth on `/sales.html`/`/api/sales/leads`, `dreamhome.events` same-millisecond ordering assumption, no monitoring/error tracking.

## 5. Decisions and why

- **`upperOnly` rooms are absent from the wrong-floor palette, not disabled.** The phase prompt's AC1 says "absent from the ground-floor palette," a stricter behavior than the existing `groundOnly` pattern (visible, greyed out, with a tooltip). Balcony is the first `upperOnly` room, so this is a genuinely new filter (`Palette.jsx`'s `visibleRooms`), left orthogonal to the existing `groundOnly` disabled-state logic rather than folding both into one rule — a ground floor DSQ is still a real (if currently unavailable) choice a player might expect to see; a balcony on the ground floor isn't a real choice at all.
- **The balcony lifestyle signal (`outdoor_priority`) does not feed the lead score.** The Phase 5 score formula is documented and fixed (`server/lib/signals.js`'s header comment, mirrored in `docs/phases/phase-5.md`) and sums to exactly 100 with no penalty. Silently adding a new lifestyle flag to the existing capped-at-15 lifestyle bucket would shift score distributions for reasons not visible in that documentation without a deliberate re-derivation of the weights. This phase's prompt asked for a signal, not a scoring change, so `outdoor_priority` is descriptive only — a future phase can fold it into scoring as a deliberate, documented decision if wanted.
- **Elevation floor width comes from each floor's actual room bounding box, independently per floor**, not a single fixed plot width. A maisonette with a narrower first floor (e.g. a balcony set back from the ground floor's footprint) should read as narrower there in the elevation, matching what the player actually built. A floor with zero rooms placed (a valid, if unusual, state — nothing requires every floor to be furnished before finishing) falls back to the nearest floor's width rather than rendering a zero-width sliver.
- **Window count per floor is `max(1, bedroom+master count on that floor)`**, not a literal, sometimes-zero bedroom count. The phase prompt asked for windows "sized to bedroom count"; a ground floor that's all living/kitchen/office would otherwise render as a windowless wall, which reads as a rendering bug rather than a deliberate design choice.
- **Roof shape is a fixed lookup table by style-pack key** (`minimalist`/`compact` → flat, `coastal` → hip, `stone` → gable), not derived from any catalogue field. The phase prompt specified the mapping exactly; adding a `roof_shape` column to `catalog_style_packs` for four fixed, prompt-specified values would be config for its own sake with nothing to tune.
- **Hip and gable roofs are visually distinguished by shape, not just fill colour**: gable is a full triangle to a single ridge point; hip is a trapezoid with a shortened flat ridge (both slopes visible, matching a real hip roof's front-elevation silhouette). This was worth the extra polygon math since the whole point of AC4 is that the four style packs read as visually distinct roofs, not just four colours on the same shape.

## 7. Addendum (2026-08-04): rooms rendered at roughly half width — real bug, found and fixed

A bug was reported: rooms rendering with their drawn SVG content (walls, floor texture, furniture) filling only about half their expected width, while the label chip and grid footprint looked correct. This turned out to be real, live in the app, not specific to any test tooling. **An earlier pass at this investigation (first cut of this addendum) wrongly concluded it was a screenshot-capture artifact. That conclusion was wrong and has been replaced by this one.**

**What went wrong with the first investigation.** The first pass mounted `RoomBlock`/`RoomArt` directly with hand-crafted props in a throwaway harness page, since dnd-kit drag-and-drop couldn't be driven through this session's browser automation. Four checks against that harness — source trace, DOM/CSS geometry, an isolated SVG-to-canvas rasterization, and an `html2canvas` capture — all showed correct full-width rendering, while CDP screenshots of the same harness showed the reported half-width symptom. That contradiction was resolved (wrongly) in favor of "the screenshot tool is lying." It wasn't. The real bug is paint-only — it doesn't show up in `getBoundingClientRect()`, `getComputedStyle()`, SVG attributes, or an isolated re-render of the same markup via `Image`/`Blob` or `html2canvas`, all of which construct a *fresh* paint rather than inspecting the *live* one. Only an actual on-screen capture of the actual live element, in its actual DOM context, shows it. The harness's crafted-props approach happened not to reproduce it reliably; a real placed room in the real running `PlotCanvas` did, every time.

**Getting a real room placed at all required solving a second, unrelated problem first**: this session's `computer` tool's `left_click_drag` action does not dispatch real `pointerdown`/`mouseup`/`click` events — confirmed by instrumenting the page with capture-phase listeners on every mouse/pointer event type, which recorded only `pointermove` events (with a `buttons` bitmask that happens to flip to `1` partway through, but no press/release event ever fires). No JS drag-and-drop library, dnd-kit included, can activate on that input. Dispatching a hand-built `PointerEvent` sequence (`pointerdown` → several `pointermove` → `pointerup`) directly against the real running app did activate dnd-kit correctly (confirmed via temporary `console.log` instrumentation in `handleDragStart`/`handleDragMove` — both fired, with `isOver`/`valid` computed correctly) and successfully placed real rooms. This is a tooling limitation worth remembering for any future live-app browser verification in this environment, separate from the room-rendering bug itself.

**Root cause, isolated by bisection on the real live element**: `RoomBlock.jsx`'s room container had `overflow: 'hidden'`. With a real placed Living Room, systematically toggling that container's live `style` properties in devtools-equivalent JS and re-screenshotting after each change showed:
- Setting `overflow: 'visible'` → renders correctly, full width.
- Restoring `overflow: 'hidden'` and adding `transform: translateZ(0)` (a common fix for compositing-layer precision issues) → still broken.
- `overflow: 'hidden'` with `border-radius: 0` → still broken (not a border-radius interaction).
- `overflow-x: 'visible'` with `overflow-y: 'hidden'` kept → renders correctly.
- `overflow-x: 'hidden'` (either alone or via the `overflow` shorthand) → broken, every time.

So specifically `overflow-x: hidden` on this container causes the browser to paint the child SVG at roughly half its declared width, despite every DOM/CSS/attribute value (`getBoundingClientRect`, `getComputedStyle`, the SVG's own `width`/`height`/`viewBox`) reporting the correct, matching size throughout. This is consistent with known Chromium rendering issues where `overflow: hidden` combined with a non-integer `devicePixelRatio` (1.5 in this environment, consistent with 150% OS display scaling) can size a clip/compositing layer incorrectly — a paint bug, not a layout or JS bug, which is exactly why nothing in `RoomArt.jsx`'s or `RoomBlock.jsx`'s actual size *math* was ever wrong (the original source trace in the first investigation pass was correct on that narrow point) and why it was invisible to every geometry-based check.

**The fix**: removed `overflow: 'hidden'` from `RoomBlock.jsx`'s room container. It wasn't doing any useful clipping under correct rendering — `RoomArt`'s SVG already matches the container's exact dimensions (`room.w * cell - 3`, the same value on both) and already applies its own `borderRadius` in its `style` prop, so the container-level clip was redundant for the room art itself. Its one real job was preventing the room's label chip (e.g. "🛁 Bathroom · 2×4m · KES 1.0M") from visually spilling into neighbouring rooms on small footprints where the label text is wider than the room. That's now handled directly on the label `<span>` instead: `display: 'inline-block'`, `maxWidth: room.w * cell - 3`, `overflow: 'hidden'`, `textOverflow: 'ellipsis'` — so a long label on a small room truncates with an ellipsis rather than either spilling (no clipping at all) or triggering the same container-level paint bug (clipping the whole container).

**Verification**: reproduced the bug in the real running app (not a harness) — placed a Living Room via a real drag (using the hand-built `PointerEvent` sequence described above, since `left_click_drag` can't drive it), confirmed the half-width rendering live, with the DOM/CSS geometry still reporting "correct" throughout, ruling out any easy geometry-based explanation and forcing the CSS-property bisection above. Applied the fix, reloaded, and placed a fresh Living Room and Kitchen the same way: both now render with the wall outline, floor texture, and furniture filling the room's full allocated width, matching the label chip and grid footprint, with no gap. Screenshotted before and after. Also placed a Balcony (this phase's new room type, on the first floor of a Maisonette) after the fix and confirmed it renders correctly too — full-width tiled texture with the railing balusters spanning the whole footprint. The elevation view (`ElevationView.jsx`) doesn't use `RoomBlock` at all and was unaffected either way; not re-verified here since it was already thoroughly checked in §6 above and has no code path in common with this bug. Production build (`npm run build`) still succeeds after the fix, bundle size effectively unchanged.

No contract or schema changes. `client/src/components/RoomBlock.jsx` is the only application file touched.

**No code was changed.** There is nothing in the room-rendering pipeline to fix; introducing a "fix" here would just be adding an unnecessary compensating factor for a problem that doesn't exist in the app, which would actively break the real (correct) rendering. Balcony and the Phase 7 elevation view were checked alongside Living Room and Kitchen specifically because they're this phase's new surface area — both measured consistent with their intended geometry (the balcony's rasterized width came in at 125/129px, matching its deliberate 1px inset balustrade border, not a bug).

If this resurfaces as a genuine user-reported issue (not just something caught in this automated environment), the next place to look is a real device/browser screenshot taken outside this session's tooling, to rule in or out whatever is specific to the CDP capture path here.
